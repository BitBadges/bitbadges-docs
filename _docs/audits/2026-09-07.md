# End-to-End Documentation Audit

## [1] Scope and Evidence

The audit covers reader journeys, protocol explanations, SDK/API/CLI examples,
navigation, rendering, and generated references. Three independent reviewers
handled protocol semantics, developer integrations, and reader journeys. The
integration pass checked the landing page, the whole rendered corpus, and the
site on desktop and mobile.

The initial corpus contained 1,972 pages: 238 narrative and builder-skill pages,
plus 1,734 generated SDK/protobuf reference pages. All pages received mechanical
rendering and link checks. Narrative pages received broad editorial review with
targeted implementation checks. Generated references received mechanical checks
and targeted source comparisons, not a field-by-field certification.

## [3] Verification

The initial suite failed because the checkout's generated public OpenAPI file
was stale. After `bun run sync`, the unchanged baseline passed 404 tests with
zero failures. The one conditional skip is the fallback test for a missing
proto tree; the real generated-proto tests ran.

The final suite passes **406 tests, zero failures**, with the same conditional
skip. Typechecking passes. The production build generates 1,983 static routes;
two existing Turbopack warnings concern broad filesystem tracing in the docs
loader. No warning was suppressed to make the build pass.

The new `site/tests/examples.test.ts` was run failing before the documentation
fixes, first over the authored pages and then over the generated references. It
parses every JSON, TypeScript, JavaScript, and shell example in the corpus. Type
and object fragments must be valid declarations or explicitly labelled
non-executable illustrations. The check does not claim type correctness or
successful network execution. A separate rendering regression test verifies that
the SDK's `mustGetBalances` example cannot swallow subsequent method sections.

## [4] Remaining Work and Improvements

### [4.1] Public EVM Endpoint Identity

On 2026-09-07, `https://evm-rpc.bitbadges.io` returned `eth_chainId = 50024`
but `net_version = 90123`. The endpoint operator should reconcile these values
and verify the signing flows that depend on them. No configuration was changed.

The same read-only check returned zero for `eth_gasPrice`. This is an observation,
not a promise that every signing path or future transaction has zero fees. The
six allowed denoms and 0.1% default taker fee matched the docs. Testnet RPC/LCD/EVM
hosts failed DNS, the site returned 403, and the API returned 503.

### [4.2] Generated Examples Need Upstream Tests

The generated SDK tree contains source-comment examples with ellipses, stale
signatures, and prose labelled TypeScript. Syntax diagnostics are not one-to-one
with defects: one missing fence in `BitBadgesUserInfo.mustGetBalances` caused
hundreds of diagnostics by swallowing subsequent reference sections. This fence,
prose misclassified as code, malformed snippets, and contradictory builder-skill
instructions were corrected in source documentation on companion SDK branches.

Fix source comments before regeneration, and add SDK-side compile/runtime tests
for complete JSDoc examples. Prefer named runnable fixtures referenced by both
JSDoc and the guides. Keep abbreviated signatures explicitly separate from
copyable examples. A wholesale reference regeneration should use the intended
released SDK revision, not silently publish every local source change.

### [4.3] Complete Journeys Need Dedicated Fixtures

Add a small integration suite for creation, minting, transfer, wrapping, claims,
and sign-in against an isolated funded environment. Assert both successful and
rejected transfers. Syntax checks cannot establish balances, approvals, plugin
availability, or changing chain state. Mainnet operations remain real operations,
even when the chosen token has no monetary value.

### [4.4] Published Versions and Live Claims

Record the source revision or released package version beside generated
references. Gate regeneration on syntax and source-example tests. Live network
status, CLI/native-binary boundaries, API policy, and third-party protocol
comparisons should have dated checks rather than unqualified promises.

### [4.5] Editorial Additions

Prefer a short prerequisite/outcome/troubleshooting structure for each journey:
which wallet signs, which assets it already owns, which approval permits the
operation, what success returns, and how to diagnose rejection. Keep the full
reference available, but link to it after the smallest complete example. Avoid
duplicating permission recipes across guides and builder instructions without
a shared tested fixture.

### [4.6] Authorization URL Helper

The SDK's `generateBitBadgesAuthUrl` in `src/core/blockin.ts` concatenates string
query values without encoding. A redirect URI containing its own query string
can change the outer authorization parameters. The guide now uses
`URLSearchParams`; the SDK implementation still needs a separate regression test
and fix. No implementation behavior was changed in the source-docs branch.
